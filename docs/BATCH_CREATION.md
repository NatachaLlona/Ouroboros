# Atomic object and array creation

POST on all eleven catalogue resources and /test accepts either one JSON object or a nonempty array of JSON objects. Token, account administration, password and read-only audit contracts are unchanged. Batch POST uses the same creation permissions: supervisor/administrator for catalogue; existing test:write permissions for /test. It is independent of administrator-only bulk PUT/DELETE and needs no bulk confirmation parameter.

## Requests and responses

A single tag creation remains:

```json
{
  "tag_name": "example",
  "display_name_tags": "Example",
  "description_tags": "Example description."
}
```

An ordered array uses the same endpoint:

```json
[
  {"tag_name": "first", "display_name_tags": "First", "description_tags": "First description."},
  {"tag_name": "second", "display_name_tags": "Second", "description_tags": "Second description."}
]
```

Both return 201. One object returns the existing full resource record. An array, including a one-item array, returns created_count and full items. For example, POST /test?display_timezone=UTC with value objects First and Second returns:

```json
{
  "created_count": 2,
  "items": [
    {"value": "First", "id": 1, "created_at": "2026-10-25T12:00:00Z", "created_at_timezone": "Europe/Lisbon", "presentation": {"display_timezone": "UTC", "dates": {"created_at": {"datetime": "2026-10-25T12:00:00+00:00", "date": "2026-10-25", "time": "12:00:00", "timezone": "UTC", "offset": "+00:00", "fallback_utc": false}}}},
    {"value": "Second", "id": 2, "created_at": "2026-10-25T12:00:00Z", "created_at_timezone": "Europe/Lisbon", "presentation": {"display_timezone": "UTC", "dates": {"created_at": {"datetime": "2026-10-25T12:00:00+00:00", "date": "2026-10-25", "time": "12:00:00", "timezone": "UTC", "offset": "+00:00", "fallback_utc": false}}}}
  ]
}
```

The response above illustrates /test with display_timezone=UTC; tag and other catalogue items use their own full record schemas. IDs and dates are illustrative, generated by the server. Each item has exactly the GET-by-ID schema, including all automatic identity/date/source fields and presentation. Array items follow request order. This is a mutation result, not a paginated GET: there is no page/page_size/count envelope and the GET 50-item page limit does not limit the result.

## Validation and atomic transactions

Each object uses the existing resource create schema. Unknown/immutable fields, invalid types, required fields, source-zone consistency, foreign keys, XOR choices, same-work relationships and existing uniqueness constraints retain their rules. No new uniqueness rule is introduced. There are no implicit references between items and no cross-table creation: every referenced ID must already exist.

Empty arrays, arrays above the configured maximum, nested arrays and non-object elements return standardized 422 VALIDATION_ERROR. Schema errors identify zero-based item locations, for example `error.details[0].loc = ["body", 1, "value"]` for the second item. Safe database/domain failures identify the active item where possible; relationship/uniqueness conflicts remain 409 RELATIONSHIP_CONFLICT and invalid resulting records remain 422. Authority/connection/commit failures may not identify an individual item. Rejected values, raw SQL and database exception messages are omitted.

The entire array uses one authorized business transaction and connection. All inserts and mandatory audit evidence commit together or all roll back. Schema validation completes before business writes. Current role/scopes/account version are rechecked under the existing membership/actor locks once per array. Items execute sequentially, using a reused parameterized INSERT ... RETURNING statement and cursor; ordinary items need no follow-up SELECT or per-item connection. This deliberate per-item insert approach provides database failure indexes. Existing row audit triggers still process each affected row. Sequence gaps after rollback are expected and are never reset.

Classification arrays also hold the existing list lock and defer tier uniqueness. Each requested tier inserts/shifts or appends against the list produced by earlier items. The locked list size is cached for the array; appends avoid empty shift queries. Later items can shift earlier created items, so one final set query refreshes all created classifications before returning them in request order. Returned tiers equal final persisted tiers. Any later invalid item rolls back earlier inserts and every shift. Concurrent API reorders serialize under the existing lock order.

## Configuration and operations

The ignored local .app.config accepts backward-compatible defaults under api. The sanitized example documents:

```json
{
  "api": {
    "max_batch_size": 300,
    "max_creation_body_bytes": 4194304
  }
}
```

| Setting | Default | Accepted values |
| --- | --- | --- |
| api.max_batch_size | 300 items | Integer 1?10000; booleans/numeric strings rejected |
| api.max_creation_body_bytes | 4194304 bytes (4 MiB) | Integer 1024?67108864 bytes |

The byte budget applies to object and array creation bodies on these twelve endpoints, before JSON parsing, including streamed requests without Content-Length. Exceeding it returns standardized 422 VALIDATION_ERROR with creation_body_too_large; no business write starts. Other endpoints keep their existing handling. The row count and byte budgets are independent: 300 arbitrarily large TEXT fields cannot be promised to fit a finite HTTP limit. Set an intentional byte budget for expected payload sizes and align any external reverse-proxy limit; do not disable resource limits. Database TEXT fields have no new per-field length constraint.

Logging's existing 1 MiB inspection ceiling and audit request/response/query/mutation capture limits are separate from request acceptance. A legitimate 300-item body larger than inspection/capture budgets can still succeed under the creation byte limit; captures explicitly record omission/truncation. Existing recursive redaction and whole token/password omission remain in place.

## Audit and QA

One HTTP interaction ID covers the whole request. Mandatory row triggers retain mutation_count inside the same transaction. The final summary identifies the resource, operation=batch_create, requested_count, created_count, a sample of at most twenty created IDs, explicit sample omission, and shifted_count. Classification shift details also sample at most twenty shifts with zero-based item_index. mutation_count includes inserted records plus automatic tier shifts; created_count counts only new records. At small capture budgets, counts take priority and ID/shift samples may be omitted. Summaries never duplicate full records. Existing bounded request/response body capture remains separate.

QA scenarios 17.1?17.6 cover schemas, 1/3/300-item arrays on every resource, order, GET equivalence, configurable limits, safe indexes, rollback, same-work/XOR/unique constraints, classification concurrency, role/version rechecks, one business connection, mandatory-audit rollback and bounded large-body capture.
